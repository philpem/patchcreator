# Embroidery geometry validation

PatchCreator's validator is deliberately separate from the compositor. It can
analyse an SVG generated by PatchCreator, an SVG subsequently edited in
Inkscape, or another SVG with a known physical size.

The current validator checks:

- minimum visible stroke width;
- minimum physical dimension of filled features;
- minimum area of each connected filled island, including tiny detached
  subpaths within a much larger SVG object.

```text
patchcreator check artwork.svg
```

By default this uses the built-in `standard-patch` design-intent profile. The
current thresholds are experimental and are intended as conservative warnings,
not guarantees that a design will or will not stitch successfully.

A machine and/or another intent profile can be selected explicitly:

```text
patchcreator check artwork.svg --machine brother-innovis-750e --intent standard-patch
patchcreator check display.svg --intent display-art
```

User profile directories use the same `--profile-path DIR` mechanism as the
`profiles` commands. A one-off stroke threshold may be supplied with
`--minimum-stroke-width MM`; feature dimension and island area currently come
from the effective profile.

Exit status is:

- `0`: validation completed with no findings, or the selected profile disables validation;
- `1`: validation completed and found embroidery concerns;
- `2`: input/profile/configuration error.

Findings are structured in the Python API (`patchcreator.validation.Finding`)
and contain a stable code, severity, object ID/tag where available, measured
physical value and threshold. Area findings use mm². Feature findings also carry
physical bounds; this is intentionally the geometry the future visual debug
layer will consume.

## Physical units

For an SVG with a `viewBox`, PatchCreator uses the document's physical
`width`/`height` and the viewBox to establish millimetres per user unit. SVGs
without a viewBox use the CSS-pixel conversion of 96 px/in. An SVG that has a
viewBox but no physical width/height is rejected because embroidery thresholds
cannot be applied meaningfully without a physical scale.

Presentation attributes and inline `style=` declarations are currently
supported. Stroke inheritance through groups is honoured, as are ordinary SVG
transforms and `vector-effect="non-scaling-stroke"`. For non-uniform transforms
the stroke validator uses the smallest linear scale, deliberately reporting the
thinnest possible physical stroke.

## Filled geometry analysis

Filled geometry is converted into a separate Shapely analysis representation in
physical millimetres. The master SVG itself is never flattened or rewritten by
validation. Rectangles, circles, ellipses, polygons/polylines and SVG paths are
supported. Cubic and quadratic Beziers and elliptical arcs are sampled only in
the analysis copy. Compound even-odd paths are reconstructed into connected
polygon islands, which is especially useful for detecting small islands in map
or traced artwork.

`feature-too-small` measures the smaller physical width/height of a painted SVG
object. `island-too-small` measures each connected polygon component separately,
so a 0.5 mm speck inside an otherwise 40 mm-wide compound path is still called
out as an island rather than being hidden by the parent object's overall bounds.

Default non-zero winding paths are conservatively unioned for this first pass;
this can overestimate area for unusual hole constructions but avoids inventing
false tiny-island findings. Exact winding/clip reconstruction can be tightened
when the narrow-gap and overlap validators need it.

Hidden content, transparent paint and geometry in definitions, masks, clip
paths and markers are ignored. CSS stylesheets and percentage stroke widths are
not part of the current validation slice; such artwork should be normalised to
presentation attributes before checking. Live text glyph outlines are also not
expanded during small-feature analysis—text remains editable and will be
handled by font-aware/export-time checks later.

This validator reports vector-geometry risk. Actual embroidery behaviour also
depends on digitisation, stitch type, density, thread, needle, fabric,
stabiliser and machine setup, so the results must not be interpreted as a jam
or stitch-quality guarantee.
